# Typfolio browser demos

A short introduction to Typfolio, two [pretext](https://github.com/chenglou/pretext) demos reproduced as Typst-rendered PDFs, and a worker batch performance demo. This is a verification fixture and a showcase, not a Typfolio package.

    npm run dev:pretext        # http://127.0.0.1:4190
    npm run build:pretext      # type checks, production build and static deployment checks
    npm run preview:pretext    # Cloudflare static hosting locally, http://127.0.0.1:4190

## Application stack and deployment

The app uses **TanStack Start** with **TanStack Router**, React and TypeScript, built with Vite. Start generates the HTML document and a typed route tree from `src/routes/`; the demo components live in `src/pages/`. Navigation uses TanStack Router links, with browser history and scroll restoration.

The deployed app is entirely client-side. Start uses [static prerendering](https://tanstack.com/start/latest/docs/framework/react/guide/static-prerendering); `src/start.ts` disables SSR by default, and only the document shell and homepage opt in to generate HTML **at build time**. Each demo lazily loads its browser-only code, so canvas, pdf.js, Web Workers and localStorage run in the browser. Visiting the homepage does not load the PDF compiler. There are no server functions, API routes, server loaders, application server or Cloudflare Worker script. The Web Workers used to compile PDFs run on the visitor's device, not at Cloudflare.

Start still emits `.build/pretext-hybrid/server` as a build tool for prerendering the homepage and shells. It is never uploaded or used to handle production requests. Deploy **only `.build/pretext-hybrid/client`**. The build writes `index.html`, `ascii.html`, `editorial.html` and `performance.html`; Cloudflare serves them at their clean route URLs. Each demo entry contains its own loading shell and hydration state, so direct visits, refreshes and query parameters work without an application server or rewrite rules. Assets keep their real paths, and missing assets and unknown routes return 404. `public/_headers` gives hashed assets immutable browser caching. Keep the emitted WASM and font files alongside the JavaScript assets.

`src/routeTree.gen.ts` is generated by Start during development/build and committed so a clean checkout can run the workspace TypeScript checks before a Vite build. Regenerate it after adding or renaming routes; do not edit it by hand. Add new URLs to the `pages` list in `vite.config.ts` so they also get static entry pages.

### Cloudflare static deployment

`wrangler.json` configures [Cloudflare static assets](https://developers.cloudflare.com/workers/static-assets/get-started/) with **no `main` entry and no server bindings**. It serves files only. No TanStack Cloudflare SSR adapter or Pages Functions are needed.

From a checkout with the pinned compiler artifact already generated:

```sh
npm ci
npm run build:pretext
npm run preview:pretext
# When ready to publish, authenticate with Wrangler and run:
npm run deploy:pretext
```

The configured project name is `typfolio-demos`; change it if the Cloudflare project uses another name. `deploy:pretext` rebuilds and checks the files before uploading only the client directory. Preview is local and needs no Cloudflare credentials. Use `npm run dev:pretext` for Vite hot reload; stop that server before previewing on the same port.

The configured production hostname is **`typfolio.kerematam.com`**, declared in `wrangler.json` with `custom_domain: true`. Deploy using the Cloudflare account containing the active `kerematam.com` zone; Cloudflare creates the domain's DNS record and HTTPS certificate. If that hostname already has a CNAME, resolve that conflict before deployment. The app is served at the subdomain's root, so no Vite base path or router changes are needed. See [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

The same client directory can be uploaded to **Cloudflare Pages** as a static site (framework preset: **None**). The included `_headers` and `404.html` work there too. A top-level `404.html` prevents Pages from treating missing assets as homepage requests. Do not select a TanStack Start SSR deployment preset or upload the sibling `server` directory.

**A fresh clone needs the compiler artifact.** `packages/wasm/generated` is gitignored, so a bare Cloudflare Git build cannot succeed with only `npm ci && npm run build:pretext`. Generate the pinned compiler first with `npm run setup:wasm && npm run build:wasm` (see [compiler build instructions](../../docs/compiler-build.md)), or use the existing GitHub CI pipeline: after browser tests pass, its `browser-demos-static` artifact contains the complete ready-to-upload site. Download and extract that artifact, then upload its contents to Cloudflare Pages. This avoids rebuilding Rust on Cloudflare and requires no production Node or Rust runtime.

`tools/check-static-demo.ts` checks that only client files are configured for deployment, no server entry is present, route entry pages and headers are emitted, the compiler hash matches the pin, and every file fits Cloudflare's **25 MiB per-asset limit**. The current compiler is about **23.2 MiB**, so future compiler growth is checked before deployment. Browser tests run against Wrangler's static asset server, cover direct visits and refreshes, and reject API calls or external requests during the demos.

## Demos

| Route | Demo | What the PDF contains |
|---|---|---|
| `/` | Typfolio overview | Introduction, why it exists, and links to the demos |
| `/ascii` | Variable typographic ASCII | One page (or an 8-page flipbook) of proportional ASCII art, glyph by glyph |
| `/editorial` | The editorial engine | Headline, drop cap, three-column body flowing around five orbs, pull quotes |
| `/performance` | 1000 PDFs on workers | A separate synthetic progress report for every document |

The header links back to the **Overview** and groups ASCII and Editorial under **Pretext**, with **Worker batch** as a separate route.

## Worker batch performance

`/performance` carries the batch controls, document heatmap, file list, PDF previews, run history and worker sweeps into the shared dark and gold layout. It uses the current callable-template API and explicitly sets `validate: false` on every batch job. PDF/UA-1 export is still selectable independently.

Each run owns its worker pool and disposes it on completion or cancellation. Leaving the route cancels an active batch or sweep. Run history is stored locally; retained PDFs live only in memory. Query parameters such as `/performance?workers=4&count=1000&autostart` support repeatable recordings. Charts use TanStack Charts 1.1.0.

The **Engine** switch (`?engine=paramdoc`) renders the same batch with the experimental paramdoc runtime from `experiments/paramdoc`: Typst typesets the report once at export time into a document with slots, and a 16 kB runtime fills the slots in Web Workers and writes tagged PDF/UA-1 without the compiler. The exported document and its two subset fonts are checked in under `experiments/paramdoc/documents/report/`; the layout is the slot dialect's version of the report (static title, tutor comment of up to three lines, no score bars). The runs panel lists one engine's runs at a time, because the two rates are an order of magnitude apart.

The app downloads and compiles the WASM module once per page lifetime, then shares that module with each compiler through the existing worker API. Workers still own separate WASM instances and compile the PDFs themselves. This avoids concurrent large cached downloads failing in Chromium while preserving normal immutable asset caching. The first batch's elapsed time includes module download and compilation; later runs reuse that module. Per-document cold timings cover worker startup and instance initialization.

## The hybrid pipeline

```
 browser                                              Typst WASM
 ┌───────────────────────────────┐   JSON input   ┌─────────────────────────┐
 │ pretext: measure + line-break │ ─────────────▶ │ Typst: place() + draw   │ ─▶ PDF bytes
 │ (canvas, Libertinus Serif)    │  positioned    │ (no line breaking, no   │
 │ obstacles, columns, rows      │  lines, glyphs │  centering, no flow)    │
 └───────────────────────────────┘  orbs, colours └─────────────────────────┘
```

- **Layout is JavaScript.** pretext decides where every line breaks, how wide it is and where it sits. `src/editorial/engine.ts` and `src/ascii/engine.ts` are pure: they return plain data.
- **Rendering is Typst.** Each template (`asciiTemplate` in `src/ascii/capture.ts`, `editorialTemplate` in `src/editorial/capture.ts`) is a loop of absolutely positioned `place(top + left, dx:, dy:, ...)` calls. Typst never breaks a line or centres a row.
- **PDF-only previews.** Both routes start in live PDF mode. There is no DOM art or editorial renderer. "Capture" freezes the current layout, stops the live pool and displays a static PDF; "Resume live PDF" restarts the animation. The ASCII flipbook records eight layouts into an eight-page PDF.
- Both templates are inline Typst strings, each the one file of a `defineTemplate` without a schema: `asciiTemplate(framesToInput(...))` and `editorialTemplate(layoutToInput(...))` are the documents to compile, typed by the TypeScript input types and not checked at runtime. Not being editor-authored files, they read their data with plain `json()` at their `schemaPath` (`/frames.json`, `/layout.json`) and need no JSON Schema file. The compiler has no remote package imports.

## Live PDF mode

Both Pretext routes open with **Live PDF mode** enabled and **Viewer** selected: ASCII at **100% zoom**, Editorial at **50% zoom**. Turning live mode off captures the current layout as a static PDF at the same route's default zoom. The machinery is shared (`src/live/`):

The ASCII preview keeps a small live **Source field** thumbnail in the PDF view's upper-right corner. It reuses the simulation's existing canvas and stays out of the exported PDF.

A thin gold border inside each ASCII PDF page marks the 440 × 448 pt artwork area, inset 14 pt from the page edge. It appears in live frames, captures and flipbooks.

Pointer coordinates are relative to the displayed PDF canvas, including its current zoom and scroll position. The ASCII grid spans the full artwork rectangle: all 50 columns reserve 8.8 pt, including empty cells. Pretext measures each proportional glyph to center it within its slot. Pointer input maps directly to the source field, so changing brightness cannot shrink or shift the interactive area.

Captures, flipbooks, worker warm-up and live compiles explicitly use `validate: false`, keeping runtime schema validation out of the performance measurements.

```
 route (rAF + pointer input)          src/live/session.ts                         browser
 ┌────────────────────────┐   frame   ┌────────────────────────────────┐   ┌──────────────────────┐
 │ pretext layout of the  │ ────────▶ │ one lane per pool worker:      │   │ pdf.js worker        │
 │ newest animated frame  │  (slot    │ acquire frame → seq → compile  │──▶│ latest-wins presenter│─▶ <canvas>
 │ (no DOM rendering)    │   free)   │ on @typfolio/workers pool      │   │ (drops stale frames) │
 └────────────────────────┘           └────────────────────────────────┘   └──────────────────────┘
```

- **Workers, not the main thread.** Frames compile on `createWorkerClient({ workerCount })`, keeping compilation off the main thread. The pool size (1-4) is a control.
- **Demand-driven.** A lane captures the newest frame only when its pool slot is free (capture → compile → hand over → capture again). There is no rAF-driven flooding and never more compiles in flight than workers. Frames produced while all slots are busy are simply never submitted.
- **Latest wins, in order.** Every captured frame gets a sequence number. Compiles finish out of order; the presenter keeps one pending PDF, paints one at a time, and drops any PDF older than the newest one already shown or being painted (the *dropped* counter).
- **pdf.js to a canvas**, double-buffered (paint offscreen, one `drawImage`), instead of re-instantiating an `<iframe>` viewer per frame. One shared pdf.js worker; `disableFontFace` so each frame's fonts are glyph outlines rather than new `FontFace`s.
- **Stale work is skipped, not aborted.** Aborting an active job terminates its worker (hard cancellation of synchronous WASM) and a fresh worker re-instantiates the WASM, so the abort signal is used only at shutdown.
- **Controls and stats.** Pool size, *Extra load* (a pure Typst script loop added to every frame so pool scaling is visible when a frame compiles in milliseconds), and *Uncapped* (advance the simulation whenever a slot frees instead of once per display frame). Stats: pretext layout ms, Typst compile ms (worker round trip), pdf.js render ms, painted fps, compile throughput, dropped frames, pool warm-up.
- **Dragging inside the PDF.** On the editorial route you can drag (and click to pause) the orbs directly on the live PDF canvas, and the text reflows around them as you move. On the ASCII route the pointer over the canvas acts as a particle attractor. This interaction layer is ordinary page-level pointer handling over the pdf.js canvas (pointer capture, coordinates mapped from canvas CSS size to stage units, hit-testing against the *current* engine state): the PDF itself is static for each frame and is simply re-typeset about 20-60 times per second. Exported PDF files are not interactive. The rasterisation scale drops to 0.6x while an orb is held, for a higher interactive frame rate.

### Three ways to view the same bytes

The live panel's **View** switch shows the PDF Typst just produced in three ways. They are the same bytes:

| Mode | What it is | Live? | Drag on the PDF |
|---|---|---|---|
| **Fast** | The bare pdf.js canvas | every frame | yes |
| **Viewer** | The same live canvas inside viewer chrome we draw ourselves: toolbar (document name, `page / pages`, zoom), gray backdrop, the page as a shadowed sheet | every frame | yes |
| **Native** | Chrome's built-in PDF viewer in an `<iframe>` on an object URL | snapshot: **Refresh** button, or an opt-in 2 s auto-refresh | no |

- Viewer zoom is a CSS resize of the live canvas; when zoom settles (400 ms) the canvas is re-rasterised at the new size, so the live loop never restarts.
- Native cannot follow frames: re-pointing Chrome's viewer re-instantiates it per frame (flicker, lost zoom/scroll), and the viewer owns pointer input, so dragging is unavailable there. While Native is shown, pdf.js painting pauses and the compile pipeline keeps running.
- The non-live result of "Capture frame" / "Flipbook" has the same switch (Viewer or Native). Viewer stacks every page vertically with scrolling and a live `page / pages` indicator; Native is the original `<iframe>`.

**Proof it is a PDF**, visible in every mode:

- **Download frame** saves the exact bytes of the displayed frame (`typfolio-ascii-frame.pdf`, `typfolio-editorial-frame.pdf`). The downloaded file is the ground truth: open it in any viewer or run `pdftotext`/`pdfinfo` on it.
- **Open in tab** opens the same bytes full-page in the browser's own viewer.
- The info line reads `PDF · 48 KB · 1 page · compiled 4 ms ago`: size from the byte array's length, page count from pdf.js, age since the compile finished.
- Only the latest frame's bytes are retained (one buffer, replaced each frame); downloads and Native snapshots copy from it on demand.

The "Capture frame as PDF" button compiles on the main thread through `@typfolio/react` and shows the static result in Viewer or Native mode.

## Font parity

pretext measures through canvas with the fonts the browser has; Typst lays out with the font files the compiler was given. `src/assets.ts` names each Libertinus Serif face by URL and uses the **same files twice**: `new FontFace('Libertinus Serif', 'url(...)', { weight, style })` registered (and awaited) before any `prepare*` call, and `createCompiler({ fonts })` / `createWorkerClient({ compiler: { fonts } })`, which fetch those URLs themselves (inside each worker for the live pool). Demo `px` are `pt` 1:1 in the PDF, and the page is the stage size.

Details that keep measured geometry aligned with the PDF:

- **Baselines use a cached font probe.** `src/measureBaseline.ts` briefly mounts a hidden line with a zero-size inline-block to measure its baseline (half-leading included), then removes it. Each font/line-height/letter-spacing combination is measured once, independently of the PDF preview. Templates use `top-edge/bottom-edge: "baseline"` and place at `y + baseline`.
- **ASCII art disables kerning and ligatures in the PDF** to preserve independently measured glyph widths. The editorial body text keeps default kerning and ligatures.
- ASCII glyph positions use measured `h(width)` gaps, including empty grid cells, rather than literal spaces. This preserves the grid's width without stretching the proportional glyphs.

Fonts: `fixtures/fonts/LibertinusSerif-{Regular,Bold}.otf` come from `typst-assets`; `-Italic.otf` and `-BoldItalic.otf` (used by the pull quotes) were added from the official Libertinus v7.051 release. The first two are byte-identical to the release.

## Not a one-to-one port

- The stage is a fixed logical size (1200x760 or 860x760) instead of the browser viewport, so it can size a PDF page. The narrow-viewport mode and text-selection handling from the original are omitted.
- The orbs' CSS `box-shadow` glow has no Typst equivalent; it is approximated by a radial gradient sampled from the same Gaussian falloff.
- Body text is 19 px Libertinus Serif (the original uses an 18 px Iowan/Palatino stack).
- ASCII glyphs sit in a fixed grid rather than packing each row by natural advances, keeping the PDF aligned with its source field and pointer at both horizontal edges.
- The mid-word breaks ("docum / ents") in narrow slots come from the original algorithm.
